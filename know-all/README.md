# 每日闲聊语料库

当前项目已经正式收缩为一套**对话式内容生产工作流**，不再继续沿着独立产品、独立前后端、独立模型 API 配置的方向推进。

## 当前定位

这个仓库现在主要承担三件事：

1. 保存项目方法论和内容规范
2. 保存审核稿与出图稿之间的统一结构
3. 保存可复用的 QA 规则与 skill 约束

它不是一个需要单独运行的内容生产产品，而是一个围绕对话生成、人工审核、最终出图展开的工作流仓库。

## 当前标准流程

后续默认按这条链路执行：

1. 你给出一个话题
2. 我先生成一份审核稿
3. 由“本地审核文档”环节为该专题在本地创建一个单独文件夹
4. 把审核稿保存成一份本地文稿文档，供你直接修改
5. 你在本地文档里改完后，明确告诉我“文稿已确认”
6. 我再从这份本地文档中读取最终内容，整理成 `ApprovedNotePack`
7. 然后才进入图片生成阶段，输出可直接上传的小红书图片组

## 当前 skill 边界

当前默认把整条链路拆成 3 个核心环节：

1. 写作 skill
   - 只负责审核稿内容本身
   - 负责标题、封面文案、知识卡内容、语气、结构、深度
   - 不负责本地落盘
2. 本地审核文档 skill
   - 只负责把审核稿写入 `outputs/YYYYMMDD_话题/01_审核稿.docx`
   - 负责专题文件夹、文稿版式、话题库超链接
   - 本地文档一旦存在，就成为审核阶段唯一 source of truth
3. 出图 skill
   - 只负责读取已确认的本地文稿 / `ApprovedNotePack`
   - 负责封面、知识卡、排版和 PNG 导出
   - 不负责回改文稿逻辑

## 专题文件夹约定

后续每个专题都单独放在 `outputs/` 下的一个文件夹里，推荐结构如下：

```text
outputs/
  20260322_红酒/
    01_审核稿.docx
    02_approved-note-pack.json
    红酒-cover.png
    红酒-card-01.png
    红酒-card-02.png
    ...
```

说明：

- `01_审核稿.docx` 是你人工修改的主文档
- 在你明确确认之前，我不会把这份文稿直接推进到出图
- `02_approved-note-pack.json` 是确认后的结构化中间稿
- 图片阶段只消费确认后的结构，不再反改文稿

## 审核稿文档规则

- 每次先生成审核稿，而不是直接生成图片
- 审核稿要保存到本地文档，方便你直接修改
- 我后续进入出图阶段时，以本地已确认文档为准，而不是以上一轮聊天文本为准
- 只有当你明确说“文稿无误 / 可以出图”时，才进入图片生成

仓库里已经准备了模板文档：

- `templates/topic_draft_template.docx`

## 审核稿与出图的边界

边界已经固定：

- 文稿阶段：只审内容
- 出图阶段：只做图片实现

也就是说：

- 文稿阶段决定“写什么”
- 出图阶段决定“怎么把已确认文稿做成图”
- 出图阶段无权擅自回改文稿
- 出图阶段也不再重新判断内容是否空、浅、满不满

如果文稿要改，必须由你明确重新打开文稿审核阶段。

## 用户反馈如何进入长期规则

这是一个持续迭代的工作流，不是每次都从零开始写。

所以默认遵守这条原则：

- 如果你的修改意见只是当前这篇的临时调整，那就只改当前专题
- 如果你的修改意见明显是“以后都要这样”的长期标准，那我不仅要改当前专题，还要同步更新对应的 skill / reference / 文档

一句话说：

`用户确认过的长期标准，会进入项目主规则，而不是停留在单篇修补。`
