# 最高优先级要求

这份规范首先要满足一个前提：

**即便开启一个新的对话，或者换一个新的 AI，只要读到这份文档，也必须能立刻理解审核稿、本地确认文档和最终出图之间的关系，并按说明产出符合要求的结果。**

所以这里的结构、字段、边界和映射规则，都应被理解为可直接执行的协议，而不只是补充说明。

# 审核文案与出图统一格式规范

## 1. 目的

这份规范统一三件事：
- 审核阶段给用户看的文稿结构
- 本地审核文稿的确认载体
- 出图阶段真正消费的结构化对象

当前统一链路为：

`聊天生成审核稿 -> 落本地 01_审核稿.docx -> 用户修改并确认 -> 读取本地文稿 -> 生成 ApprovedNotePack -> 出图`

## 2. 总原则

一旦用户确认本地文稿，图片阶段不再重写内容，只负责：
- 版式
- 换行
- 字号微调
- slogan、badge、背景和视觉实现

也就是说：
- 文稿阶段决定“写什么”
- 本地文稿阶段决定“最终以哪一版为准”
- 出图阶段决定“怎么放到图上”

## 3. 强制协议与推荐实践

### 3.1 强制协议

以下规则必须遵守：
- 本地审核文稿是进入出图前的唯一确认载体
- 用户未明确确认前，不得固化 `ApprovedNotePack`
- `ApprovedNotePack` 的核心字段结构必须稳定
- 出图阶段不得擅自回改文稿
- 出图阶段不得新增审核辅助标签、chips、底部提示语等额外内容

### 3.2 推荐实践

以下做法默认推荐：
- 专题文件夹按统一命名方式组织
- 审核稿按固定协议模板输出
- `cards[].highlights[]` 只在确有必要时使用
- 封面背景尽量做主题相关，而不是单纯抽象底色

## 4. 本地审核 docx 的唯一允许实现

从现在开始，本地审核文档只能通过下面这条链路生成：

`UTF-8 结构化源文件 -> tools/write_review_docx.py -> outputs/YYYYMMDD_话题/01_审核稿.docx`

这是唯一允许实现。

明确禁止：
- shell 内联大段中文、emoji、中文路径直接拼 docx
- 把专题专用临时脚本当成默认入口
- 绕过本地文稿确认环节直接进入出图

## 6. 本地审核文档规则

### 6.1 文档地位

本地审核文稿是审核阶段唯一 source of truth。

这意味着：
- 聊天中的审核稿只负责先生成
- 真正进入下一阶段前，以本地文稿为准
- 如果本地文稿和聊天稿不一致，以本地文稿为准

### 6.2 进入出图的条件

只有当用户明确表达以下意思之一时，才进入出图：
- 文稿无误
- 可以出图
- 以本地文档当前内容为准

## 7. ApprovedNotePack 标准结构

```json
{
  "topic": "红酒",
  "title": "红酒这5件事别想当然🍷",
  "cover": {
    "title": "很多人喝红酒，但没真搞懂红酒",
    "subtitle": "从颜色到醒酒，这几件事最容易想当然",
    "points": [
      {
        "text": "红酒颜色不是果肉给的",
        "mark_raw": "🍇",
        "mark_render": "红"
      }
    ]
  },
  "cards": [
    {
      "id": "01",
      "title": "红酒颜色不是果肉给的",
      "mark_raw": "🍇",
      "mark_render": "红",
      "paragraphs": [
        "第一段……",
        "第二段……",
        "第三段……"
      ],
      "highlights": [
        "葡萄皮",
        "一起发酵"
      ]
    }
  ],
  "hashtags": [
    "#红酒知识",
    "#葡萄酒入门",
    "#每日闲聊语料库"
  ],
  "render_options": {
    "top_tags": false,
    "bottom_tips": false,
    "closing_page": false,
    "theme_cover_required": true
  }
}
```

补充说明：
- `title` 是平台发布标题，必须符合平台长度规则
- `cover.title` 是封面主标题，可与平台标题不同

## 8. 字段说明

### 8.1 cover.points[]

封面列点必须拆成：
- `text`
- `mark_raw`
- `mark_render`

规则：
- 封面列点默认与知识卡数量保持一致
- 只有在用户明确要求压缩信息量时，才允许少于知识卡数量

### 8.2 cards[].paragraphs[]

正文必须用段落数组，不再用一个大字符串临时拼接。

推荐：
- 每张卡 2 到 3 段
- 第一段：现象 / 误区
- 第二段：Why
- 第三段：必要时补限定条件、补充说明或场景

### 8.3 cards[].highlights[]

可选字段，用于标记可视化强调的短语。

规则：
- 只能来自已确认正文
- 不能借此偷偷重写内容

### 8.4 render_options

用于明确渲染阶段行为。

当前稳定键包括：
- `top_tags`
- `bottom_tips`
- `closing_page`
- `theme_cover_required`

## 9. emoji 与渲染替代

为避免 emoji 在图片中变成方框：
- `mark_raw` 保留文稿阶段原始 emoji
- `mark_render` 提供稳定渲染替代

规则：
- `mark_render` 应作为独立 badge，而不是硬拼进标题正文

## 10. 出图阶段禁止新增的内容

禁止新增：
- 顶部 tags / chips
- 底部提示语
- “适合直接上传”之类的工作流提示
- 分类标签
- 结构性辅助标签

另外：
- `正文分段` 这种审核辅助标签，不得进入最终图片

## 11. 全局固定视觉常量

当前固定 slogan：

`把日常话题讲明白，让闲聊更有料`

规则：
- 每张知识卡顶部都应出现 slogan 条
- 首页封面中 slogan 应更突出
- 知识卡中的 slogan 视觉权重应轻于标题栏

## 11.1 固定模板参数入口

出图阶段默认不靠“临场审美发挥”决定版式，而是使用固定模板参数。

当前固定模板族为：
- `cover-template-v1`
- `knowledge-card-template-v1`

这些模板参数的完整说明统一放在全局生图 skill reference：
- `C:\Users\94895\.codex\skills\daily-chat-corpus-card-renderer\references\render-spec.md`

理解方式：
- 这份仓库文档负责定义流程边界和结构协议
- 生图 skill reference 负责定义默认视觉模板和参数范围

默认原则：
- 新 AI 默认沿用固定模板族
- 可以在模板允许范围内微调字号、行距、面板高度、badge 尺寸、slogan 宽度等参数
- 不应在没有用户明确要求的情况下，擅自发明一套全新结构

### 12.1 默认审核稿模板

- 🍷 列点 3

#话题

### 12.2 强制字段

必须出现：
- `专题`
- `标题`
- `封面`
- `主标题`
- `副标题`
- `封面列点`
- 每张卡的：
  - `知识卡 N`
  - `标题`
  - `标记`
  - `正文`
- `#话题`

### 12.3 禁止写法

禁止：
- 把 `正文` 改写成 `正文分段`、`内容`、`展开`
- 把正文写成一整坨不编号文本
- 临时新增未定义的小节标题

## 13. 审核稿 -> ApprovedNotePack 固定映射规则

### 13.1 标题映射

- `专题：...` -> `topic`
- `标题：...` -> `title`
- `主标题：...` -> `cover.title`
- `副标题：...` -> `cover.subtitle`

### 13.2 封面列点映射

- `封面列点` 下的每一条 -> `cover.points[]`
- 如有 emoji，拆入 `mark_raw`
- 如有稳定替代标记，写入 `mark_render`

### 13.3 知识卡映射

- `知识卡 N` -> `cards[]`
- `标题：...` -> `cards[].title`
- `标记：raw=... / render=...` -> `cards[].mark_raw / mark_render`
- `正文` 下的编号段落 -> `cards[].paragraphs[]`

### 13.4 审核辅助标签处理

以下只作为解析锚点存在，不得进入最终图片：
- `专题`
- `标题`
- `封面`
- `封面列点`
- `知识卡 N`
- `标记`
- `正文`
- `#话题`

### 13.5 缺失字段回退

回退顺序：
1. 先看本地确认文稿里是否有等义字段
2. 再做安全字段归一化
3. 如仍无法确定，则停止自动进入出图，要求人工确认

## 14. 边界

- 审核阶段：只审内容
- 本地文稿阶段：只做确认载体
- 出图阶段：只做图片实现

出图阶段默认不得：
- 擅自回改文稿
- 重新判断内容深浅
- 绕过本地确认文稿直接用聊天稿出图

## 15. 一句话总结

`审核稿先落成本地文稿，本地文稿确认后再固化为 ApprovedNotePack，最后才进入出图；这条链路里，本地确认文稿是唯一闸口。`
