# 审核文案与出图统一格式规范

## 1. 目的

这份规范用来统一三件事：

- 审核阶段给用户看的文稿结构
- 本地审核文档的确认载体
- 出图阶段真正喂给渲染器的结构

之前的问题本质上是：

- 审核稿是自然语言块
- 出图稿是临时拼接文本
- emoji、段落、封面点位、装饰元素没有稳定字段
- 审核确认有时停留在聊天文本里，没有一个明确的本地定稿载体

所以现在统一采用：

`聊天生成审核稿 -> 保存为本地审核文档 -> 用户修改并确认 -> 读取本地文档 -> 整理为 ApprovedNotePack -> 出图`

## 2. 总原则

一旦用户确认本地文稿，出图阶段不再重写内容，只做这几类事：

- 版式排布
- 文本换行
- 字号微调
- 封面主题背景生成或本地构图
- emoji / 图形标记的渲染替代

也就是说：

- 审核稿决定“写什么”
- 本地确认文档决定“最终以哪一版为准”
- 出图稿决定“怎么放到图上”

它们不是三套内容，而是一条有明确闸口的链路。

## 3. 本地专题文件夹规范

每个专题都应有自己的本地文件夹。

推荐结构：

```text
outputs/
  20260322_红酒/
    01_审核稿.docx
    02_approved-note-pack.json
    红酒-cover.png
    红酒-card-01.png
    红酒-card-02.png
    ...
```

推荐约定：

- `01_审核稿.docx`：用户直接修改的主文档
- `02_approved-note-pack.json`：用户确认后的结构化中间稿
- 图片文件：最终交付物

## 4. 本地审核文档规则

### 4.1 文档地位

本地审核文档是进入出图前的唯一确认载体。

也就是说：

- 聊天里的审核稿只负责先生成
- 真正进入下一阶段前，以本地文档为准
- 如果用户改了本地文档，而聊天里没同步，那也以本地文档为准

### 4.2 进入出图的条件

只有当用户明确表达以下意思时，才进入出图：

- 文稿无误
- 可以出图
- 以本地文档当前内容为准

在此之前，不进入 `ApprovedNotePack` 固化环节。

## 5. 统一格式名称

建议后续所有最终审核通过的内容，内部都按一个统一对象理解：

`ApprovedNotePack`

## 6. ApprovedNotePack 标准结构

```json
{
  "topic": "白酒",
  "title": "每日闲聊语料库｜白酒：很多人喝了很多年，其实一直没搞懂它 🍶",
  "cover": {
    "title": "白酒这东西，真不是‘辣一点的酒’",
    "subtitle": "很多人喝了很多年，其实一直没搞懂它",
    "points": [
      {
        "text": "白酒其实是蒸馏酒",
        "mark_raw": "🥃",
        "mark_render": "酒"
      },
      {
        "text": "香型不是香精味",
        "mark_raw": "👃",
        "mark_render": "香"
      }
    ]
  },
  "cards": [
    {
      "id": "01",
      "title": "白酒其实是蒸馏酒",
      "mark_raw": "🥃",
      "mark_render": "酒",
      "paragraphs": [
        "很多人一提白酒，第一反应就是‘粮食发酵出来的酒’。这话不算错，但只说到一半。",
        "白酒前面当然也要发酵，但它和黄酒、米酒最大的区别，是后面还有一步蒸馏。前面先把粮食发酵成酒醅，后面再把酒汽蒸出来、冷凝成酒，所以酒精度会一下上去，味道也更集中。",
        "这也是为什么白酒入口常常更冲。它不是那种发酵完直接喝的酒，而是把酒精和风味又往上提了一次。"
      ]
    }
  ],
  "hashtags": [
    "#白酒知识",
    "#白酒入门",
    "#每日闲聊语料库"
  ],
  "render_options": {
    "top_tags": false,
    "bottom_tips": false,
    "closing_page": false,
    "theme_cover_required": true
  }
}
```

## 7. 字段说明

### 7.1 cover.points[]

封面列点必须拆成：

- `text`
- `mark_raw`
- `mark_render`

不能再写成一整句临时拼接文本。

### 7.2 cards[].paragraphs[]

这是最关键的统一点。

以后卡片正文不再用一个大字符串临时塞进去，而是必须用段落数组。

这样可以保证：

- 审核阶段就能看清楚段落结构
- 本地文档修改时也能保留段落边界
- 出图阶段直接逐段排版
- 不会把三段内容压成一整坨
- 不需要靠 `\n\n` 临时猜哪里换段

推荐：

- 每张卡 2 到 3 段
- 第一段：现象 / 误区
- 第二段：Why
- 第三段：必要时补场景或进一步解释

### 7.3 cards[].highlights[]

这是一个可选字段，用来标记“这张卡里最值得视觉强调的短语”。

推荐：

- 每张卡 1 到 3 个短语
- 必须直接来自已审核通过的正文原文
- 适合强调数字、误区关键词、关键结论、功能对比词

不要：

- 临时新写一句摘要塞进去
- 把整段都当成 highlight
- 为了好看乱标，最后满屏都是重点

渲染阶段可以用它来做：

- 加粗
- 强调色
- 轻底色标记

但不能借它偷偷重写内容。

### 7.4 hashtags[]

统一使用数组，不再在最后临时拼接长字符串。

## 8. emoji 与渲染替代规则

这是为了解决封面或卡片里 emoji 变方框的问题。

### 8.1 原因

审核稿里可以使用正常 emoji，例如：

- 🥃
- 👃
- ⏳
- 📅

但本地图片渲染环境不一定能稳定显示这些 emoji。在某些字体或绘图库下，会直接变成方框。

### 8.2 统一规则

所以以后每个图形标记都保留两套字段：

- `mark_raw`
  - 给审核稿和本地文档使用
- `mark_render`
  - 给最终图片使用，采用稳定的替代标记

## 9. 出图阶段禁止新增的内容

渲染阶段禁止再临时加这些内容：

- 顶部 tags / chips
- 底部提示语
- “适合直接上传”之类工作流提示
- 分类标签
- 位置标签
- 结构说明标签

渲染器只能消费 `ApprovedNotePack` 里已有的字段。

## 10. 审核阶段的标准输出格式

以后审核稿建议默认按这个格式输出：

```markdown
标题：...

封面：
主标题：...
副标题：...
封面列点：
1. [raw emoji] 点位文案
2. [raw emoji] 点位文案

知识卡 1：
标题：...
标记：raw=🥃 / render=酒
正文分段：
1. ...
2. ...
3. ...

知识卡 2：
...

#话题：
- #...
- #...
```

## 11. 出图阶段的标准输入顺序

默认顺序是：

1. 生成审核稿
2. 保存 `01_审核稿.docx`
3. 用户在本地文档中修改
4. 用户明确确认文稿无误
5. 从本地文档读取内容
6. 整理成 `ApprovedNotePack`
7. 渲染图片

## 12. 当前执行边界

- 审核阶段：只审内容
- 本地文档阶段：只做用户最终确认
- 出图阶段：只做图片实现

出图阶段默认不得：

- 擅自回改文稿
- 重新判断内容够不够深
- 重新判断图片“看起来空不空”并借机回改内容
- 绕过本地已确认文档，直接用旧聊天文本出图

## 13. 一句话总结

`以后审核稿先落成本地文档，本地文档确认后再固化为 ApprovedNotePack，最后才进入出图；这条链路里，确认文档是唯一闸口。`
