# 对话式内容生产工作流方案

## 1. 为什么要从“产品”改为“对话式工作流”

项目早期曾尝试向独立产品方向推进，包括：

- 浏览器页面
- 本地 HTTP 服务
- 文案模型配置
- 图片模型配置
- 文案生成、审核、出图的网页流程

但复盘后发现，这条路线的成本和目标并不匹配。

为了把它做成产品，需要持续承担：

- 模型 API 配置
- 单独的 token 计费
- 前后端维护
- 接口兼容问题
- 图片模型适配问题
- 页面状态管理和运行错误处理

而项目真正想解决的问题，其实是：

- 高质量地产出一篇篇符合要求的小红书知识卡片笔记
- 保持内容风格稳定
- 能持续迭代和改稿
- 能快速让新的 AI 模型接手既有规范

因此，项目重新定义为：

`一个以对话为入口、以规范和 skill 为核心的内容生产工作流。`

---

## 2. 新方案的核心思路

在新方案下：

- 不再优先追求“产品壳”
- 不再优先追求“用户自己配置 API 后独立运行系统”
- 优先保留真正有复用价值的部分：
  - 内容规范
  - 研究方法
  - QA 标准
  - skill 体系
  - prompt 资产

这意味着：

- 具体每一篇内容，直接通过和 AI 的对话完成
- 项目仓库本身，变成“工作方法与规范资产库”
- skill 用来让新的 AI 模型快速进入状态
- 人工仍保留在关键节点做判断和修改

---

## 3. 新工作流的标准步骤

### Step 1：用户给出话题

用户输入一个日常话题，例如：

- 城市
- 饮食
- 品牌
- 商超
- 汽车
- 新能源车
- 生活方式符号

### Step 2：AI 先做研究与知识点筛选

AI 根据既有规范，先完成：

- 判断这个话题是否适合写
- 拆出 2 到 5 个有效知识点
- 识别哪些点普通，哪些点更有记忆点
- 找出哪些点容易写虚、容易凑数、容易说教

这个阶段的目标，不是出成稿，而是先把“写什么”想清楚。

### Step 3：AI 生成小红书笔记草稿

根据内容规范，生成：

- 标题
- 封面文案
- 若干知识卡
- `#话题`

此时输出的是“可改的草稿”，不是直接发布的终稿。

### Step 4：人工审核与修改

用户对草稿进行人工判断，例如：

- 哪个知识点太普通
- 哪个知识点发虚
- 哪句话太像旁白
- 哪段太像说教
- 哪张卡片太长或太短

AI 根据反馈继续改稿，直到内容真正符合要求。

### Step 5：需要时再补图片策略

当文案定稿后，再决定是否补充：

- 配图思路
- 卡片视觉提示词
- 封面设计建议
- 图文版式建议

注意：这里的“图片”不再是项目的核心目标，而是可选的后置环节。

---

## 4. 新方案下保留的人机分工

### AI 负责

- 研究与知识点拆分
- 结构化写稿
- 风格对齐
- QA 检查
- 根据用户反馈持续重写

### 人工负责

- 判断选题值不值得写
- 判断哪些点发虚、凑数、说教
- 决定最终是否采用某版文案
- 决定是否继续做图片或发布

也就是说，新方案不是“完全手工”，也不是“全自动发布”，而是：

`AI 负责高效生产，人工负责关键判断。`

---

## 5. 当前仓库里真正有价值的长期资产

### 5.1 原始项目规划资料

- `项目计划书与执行文档：【每日闲聊语料库】.docx`

这是项目的最初业务背景资料。

### 5.2 内容规范文档

- `小红书闲聊语料库内容规范与写作技能说明.md`

这是目前最重要的内容资产之一，已经沉淀了：

- 账号风格要求
- 知识点结构标准
- 标题和封面规则
- 话题类型判断
- 禁用表达和常见问题

### 5.3 prompt / QA 规则参考文件

- `config/prompts/research.json`
- `config/prompts/writing.json`
- `config/qa/rules.json`

这些文件虽然不再作为“产品运行时配置”使用，但仍然很有价值，因为它们可以作为：

- 新模型接手时的参考规范
- 对话生成时的隐式工作标准
- 后续 skill 迭代的依据

### 5.4 skill 体系

项目已经沉淀出的 skill 思路包括：

- 研究
- 写作
- QA 审稿
- 卡片渲染
- 模型适配
- 批量评估
- 工作流构建

这些 skill 的价值在于：

- 新模型可以快速进入既定工作方式
- 不用重新摸索风格和流程
- 可以持续复用

## 6. 为什么前后端产品化内容被判定为冗余

在新方案下，这些内容不再是主干能力：

- 前端页面
- 本地 HTTP 服务
- 文案模型与图片模型的页面配置
- 浏览器里的状态管理
- 图片下载按钮、API 测试按钮等产品交互
- Node 运行环境和构建产物

它们的共同问题是：

- 维护成本高
- 和核心目标距离远
- 容易把精力从“内容质量”转移到“产品工程问题”

所以在新的方向下，这些内容统一视为：

`阶段性试验产物，而不是长期核心资产。`

---

## 7. 新方案下的推荐使用方式

以后建议这样使用这个项目：

### 方式一：直接对话产出单篇内容

适合日常生产。

流程：

1. 给出话题
2. 让我先研究
3. 再写草稿
4. 你提修改意见
5. 我继续修
6. 得到终稿

### 方式二：先做方法论沉淀，再批量应用

适合你后面准备规模化产出时使用。

流程：

1. 先用几个样稿把标准打稳
2. 总结合格与不合格的写法
3. 再把这些标准沉淀成更稳定的 skill 和规范

### 方式三：对单个模块做专项优化

适合后续提升内容质量时使用。

例如只优化：

- 标题
- 知识点筛选
- QA 标准
- 冷门点质量
- 图片提示词

---

## 8. 后续真正值得继续投入的方向

在新方案下，后续值得继续投入的不是“再做一个系统”，而是：

1. 继续打磨内容规范
2. 继续补强 skill 体系
3. 继续沉淀提需求模板
4. 继续完善不同题材的话题研究方法
5. 继续积累高质量样稿和负例

这些东西越扎实，对任何模型都越有迁移价值。

---

## 9. 一句话总结新方案

`每日闲聊语料库` 不再被视为一个独立产品，而是一个通过对话直接驱动的内容生产工作流；真正长期保留的是规范、方法、skill 和判断标准，而不是前后端产品壳。
