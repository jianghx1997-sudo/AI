# 对话式内容生产工作流方案

## 最高优先级要求

无论是新对话还是新 AI，这套流程都必须能被立刻接手，并稳定产出符合要求的审核稿、本地审核文稿和最终图片。

## 为什么改成对话式工作流

项目早期曾尝试往“独立产品”方向推进，包括网页、模型 API 配置、浏览器工作台和一体化流水线。

复盘后确认，这条路线的维护成本高于实际收益。当前更合理的方式是：

`以对话为入口 -> 以本地审核文稿为确认载体 -> 以最终图片为交付物`

## 当前标准流程

### Step 1：用户给出话题
例如：
- 城市
- 饮品
- 食物
- 汽车
- 生活方式符号

### Step 2：写作阶段生成审核稿
审核稿包含：
- 标题
- 封面主标题 / 副标题 / 封面列点
- 2 到 6 张知识卡
- `#话题`

### Step 3：本地审核文档阶段落盘
为该专题创建：

```text
outputs/YYYYMMDD_话题/01_审核稿.docx
```

这是审核阶段的唯一确认载体。

### Step 4：用户直接修改本地文稿
用户在 Word 中修改并确认。

### Step 5：从本地文稿读取并固化
确认后读取本地文稿，生成：

```text
outputs/YYYYMMDD_话题/02_approved-note-pack.json
```

### Step 6：出图
从 `ApprovedNotePack` 进入图片阶段，输出：
- 1 张封面
- N 张知识卡

## 三段职责

### 写作 skill
- 只负责审核稿内容
- 不负责本地文档落盘

### 本地审核文档 skill
- 只负责 `01_审核稿.docx`
- 负责专题文件夹、docx 版式、话题库超链接

### 出图 skill
- 只负责读取已确认文稿并出图
- 不负责回改文稿

## 本地审核 docx 的唯一允许实现

本地审核文档必须通过下面这条链路生成：

`UTF-8 结构化源文件 -> tools/write_review_docx.py -> 01_审核稿.docx`

这是唯一允许实现。

明确禁止：
- shell 内联大段中文、emoji、中文路径直接拼 docx
- 使用专题专用临时脚本作为默认入口

## 专题文件夹约定

```text
outputs/
  20260324_鸡尾酒/
    01_审核稿.docx
    02_approved-note-pack.json
    话题-cover.png
    话题-card-01.png
    ...
```

## 话题库约定

统一使用：
- [topic_library_final.xlsx](E:\AI\know-all\outputs\topic_library_final.xlsx)

补充约束：
- 不新增筛选功能
- 保留手工新增列，例如“发布日期”
- 新增话题时，只补超链接，不覆盖其他列

## 边界

- 文稿阶段：只审内容
- 本地文稿阶段：只做确认载体
- 出图阶段：只做图片实现

出图阶段默认不得：
- 擅自回改文稿
- 重新判断内容深浅
- 绕过本地确认文稿直接用聊天稿出图

## 异常处理入口

如果流程中出现：
- 本地文稿乱码
- 话题库无法保存
- 本地文稿与聊天稿不一致
- pack 无法生成
- 图片内容缺失或排版异常

- [异常处理规则](E:\AI\know-all\docs\异常处理规则.md)
