# SeeYou Wardrobe 项目顶层规划

更新时间：2026-05-12

## 一、项目定位

SeeYou Wardrobe 不应只被定义为“AI 识别衣服并展示的相册”，更准确的定位是：

> 个人衣橱数据资产 + 场景化穿搭决策 + 服装消费建议系统。

项目的主线不是数字人试穿本身，而是让用户把真实衣橱交给系统之后，系统能持续帮助用户减少选择成本、提升搭配质量，并最终给出可信的购买建议。

数字人试穿是重要增强能力，但不是商业化的唯一前提，也不应过早成为项目主干。

## 二、核心产品闭环

推荐的产品主循环如下：

```text
上传衣服
  -> AI 自动识别
  -> 用户快速修正
  -> 形成衣橱画像
  -> 每日/场景穿搭推荐
  -> 用户反馈喜欢、不喜欢、已穿
  -> 推荐逐步变准
  -> 发现衣橱缺口
  -> 推荐应购单品
```

如果没有用户反馈和学习机制，系统会停留在“服装相册”。真正的价值来自衣橱数据、穿着行为、推荐反馈和消费建议之间的长期闭环。

## 三、阶段路径

### Phase 0：工程地基修正

目标：让当前原型具备长期迭代的工程基础。

优先事项：

- 修正文档与代码现实不一致的问题，例如当前项目已经实际使用 SQLite，但旧文档仍提到 JSON 待迁移。
- 补齐 `.env.example`，明确 `PORT`、`UPLOAD_DIR`、`MOCK_AI`、各 AI Provider Key 的配置方式。
- 修正上传流程：当前“AI 识别”时已经保存入库，后续“保存到衣橱”只是弹窗，产品语义需要改为“识别预览 -> 确认保存”。
- 后端从单文件 `server.js` 逐步拆分为 routes、services、repositories。
- 增加上传图片和数据库备份策略，避免真实用户数据误删。
- 补真实 PWA 能力：当前有 manifest 和依赖，但尚未真正启用 `vite-plugin-pwa`。
- 建立基础验证命令：后端健康检查、前端构建、关键 API smoke test。

### Phase 1：高质量衣橱录入

目标：让用户愿意一次性录入足够多的衣服，并且数据质量可用。

重点能力：

- 单图上传、拍照上传、相册选择。
- 多图批量上传。
- AI 识别后可快速编辑。
- 结构化标签：类别、颜色、季节、风格、场合、材质、版型、厚薄、正式度。
- 搜索、筛选、收藏、最近穿过、很久没穿。
- 衣物信息完整度提示。
- 图片裁剪、背景清理或视觉规范化，让衣橱页面更整洁。

核心指标：

- 用户平均录入衣物数量。
- AI 识别后修改率。
- 7 日后回访率。
- 衣物标签完整度。

### Phase 2：衣橱理解与统计

目标：让系统先理解用户有什么，再进入推荐。

重点能力：

- 分类分布：上衣、裤子、裙子、外套、鞋子、配饰数量。
- 季节覆盖：春/秋、夏季、冬季、四季衣物是否均衡。
- 场景覆盖：通勤、休闲、约会、运动、正式、旅行是否缺失。
- 颜色结构：基础色、亮色、同色系集中度。
- 穿着频率：常穿、少穿、长期闲置。
- 用户偏好：常选颜色、风格、版型、场合。

这一阶段可以开始输出用户可理解的洞察，例如：

- “你不是衣服少，而是缺少适合通勤的下装。”
- “你的上衣很多，但鞋子搭配空间偏窄。”
- “冬季衣物覆盖较好，夏季下装不足。”

### Phase 3：可解释穿搭推荐

目标：根据天气、场景、季节和用户偏好生成可信搭配。

当前最小原型状态：

- 已接入高德天气实况查询接口：`GET /api/weather/current`
- 已实现规则推荐接口：`GET /api/recommendations/outfits`
- 已提供前端“今日推荐”页面，支持手动天气/温度/场景输入
- 高德 API Key 未配置时，推荐页可继续使用手动天气输入

推荐策略建议采用“规则引擎 + AI 排序 + 用户反馈”的混合架构，而不是一开始完全依赖大模型。

推荐输入：

- 天气：温度、降雨、风力、湿度。
- 场景：通勤、休闲、约会、运动、正式、旅行。
- 用户偏好：颜色、风格、保守或大胆程度。
- 衣物状态：是否收藏、是否近期穿过、是否适合当前季节。
- 搭配规则：类别完整性、颜色协调、厚薄匹配、正式度匹配。

推荐输出应包含理由，例如：

> 今天 13-18°C，建议加一件外套；你选择了通勤场景，所以搭配深色裤子和简约上衣。

可解释性会显著提升用户信任，也便于调试推荐效果。

### Phase 4：衣橱缺口分析与商业化

目标：基于用户真实衣橱，推荐真正缺失的单品。

先做“缺口诊断”，再做“商品推荐”。不建议一开始直接接商城或大面积广告。

典型缺口：

- 缺一双适合通勤的深色鞋。
- 夏季下装不足。
- 正式场合衣物不足。
- 外套颜色过于集中。
- 有很多单品无法组成完整搭配。

购买建议应包括：

- 推荐品类。
- 推荐颜色。
- 推荐价格区间。
- 推荐材质和风格。
- 能搭配用户现有的哪些衣物。

潜在商业化方式：

- 商品 CPS / 联盟分佣。
- 品牌合作。
- 付费高级衣橱分析。
- 订阅制穿搭顾问。
- 面向服装店、买手店或造型师的 B2B 工具。

当前最值得优先验证的是“衣橱缺口分析 + 精准购买建议”，它比单纯虚拟试穿更容易落地。

### Phase 5：数字人试穿

目标：增强搭配预览和购买转化，但不要把它作为早期商业化前提。

建议分级实现：

1. 平铺搭配图：展示上衣、下装、鞋子、配饰组合，成本低、稳定性高。
2. 模特风格预览：用通用模特展示类似搭配风格，不追求用户本人高度一致。
3. 用户数字人：基于用户照片或身体数据生成更接近本人的试穿效果。
4. 购买前虚拟试穿：对推荐商品生成“与现有衣橱搭配后的上身效果”。

不要太早承诺“真实上身效果”。早期生成质量如果不够稳定，反而会降低用户信任。

## 四、建议技术架构

早期继续使用 Node.js + Express + SQLite 是合理的。项目当前最大的风险不是高并发，而是产品逻辑、数据质量和推荐可信度。

建议演进为模块化单体：

```text
backend/
  server.js
  routes/
    clothes.js
    uploads.js
    outfits.js
    recommendations.js
    wardrobeAnalysis.js
  services/
    aiRecognitionService.js
    wardrobeService.js
    recommendationService.js
    weatherService.js
    tryOnService.js
  repositories/
    clothesRepository.js
    outfitsRepository.js
    usersRepository.js
  adapters/
    ai/
      mock.js
      volcano.js
      aliyun.js
      baidu.js
    weather/
      qweather.js
  data/
    wardrobe.db
  uploads/
```

前端建议保持 Vue 3 + Vite + Vant，但逐步补齐：

- 复用组件目录 `components/`。
- 状态管理目录 `stores/`。
- 页面级模块：衣橱、上传、推荐、分析、个人设置。
- 移动端优先交互。
- 真实 PWA 离线缓存和安装体验。

## 五、数据模型建议

现有 `clothes` 表可以保留，但后续应逐步扩展。

建议核心表：

- `users`：用户信息、身体数据、风格偏好、隐私授权。
- `clothes`：衣物主表。
- `outfits`：搭配方案主表。
- `outfit_items`：搭配与衣物的多对多关系，不建议长期用 JSON 数组保存关联。
- `wear_logs`：穿着记录。
- `weather_snapshots`：天气快照。
- `recommendation_logs`：推荐记录和用户反馈。
- `shopping_gaps`：衣橱缺口。
- `product_recommendations`：商品推荐记录。

特别重要的是 `recommendation_logs`。没有推荐日志，就无法知道系统推荐过什么、用户接受了什么、为什么失败，也无法持续优化推荐质量。

## 六、AI 能力设计

AI 不应只用于图片识别，应分层使用：

1. 视觉识别：从图片识别类别、颜色、材质、季节、风格。
2. 标签修正：基于用户修改沉淀更准确的规则或偏好。
3. 搭配解释：把规则推荐结果转成用户能理解的话。
4. 缺口分析：根据衣橱结构推断应该补什么。
5. 试穿生成：在用户信任和数据基础足够后再逐步接入。

早期最值得投入的是“识别准确率 + 可解释推荐”，不是数字人生成。

## 七、对当前代码库的近期优化建议

最优先：

1. 更新 `CLAUDE.md` 和 `README.md`，同步“当前已使用 SQLite”的事实。
2. 修正上传保存流程，将识别预览和确认保存分离。
3. 补搜索功能，因为 README 已经声明支持搜索。
4. 启用真正的 PWA 插件配置。
5. 将后端 `server.js` 拆为路由层和服务层。
6. 补 `.env.example`。
7. 增加 `outfits`、`wear_logs`、`recommendation_logs` 的最小可用设计。
8. 先做一个“今日推荐”原型：天气可以先手动输入，场景由用户选择，推荐先用规则生成。

## 八、最终判断

原始规划方向成立，阶段拆分也合理，但建议调整重心：

不要把项目理解为“最终做数字人试穿”。更准确地说，它应该是“用户个人衣橱的智能决策系统”。

数字人是放大器，不是发动机。

真正的发动机是：

- 衣橱数据。
- 穿搭推荐。
- 用户反馈。
- 缺口分析。
- 精准消费建议。

只要这个主循环成立，数字人试穿、商品推荐、会员服务、品牌合作都会有更稳的落地基础。
